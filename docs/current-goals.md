## 需求分析与取舍

课程当前重视参考 App 的功能、视觉与交互还原，以及可实际演示的完成度和复杂度。参考对象继续使用“我的华为”，美团、KFC、淘宝只是老师举例，不混用多套视觉规范。

校园用户需要报修、查询进度、参加维修活动，也有二手电脑配件交易和硅脂等维修耗材购买需求；社团需要发布活动、处理服务并提供交流空间。因此采用以下映射：选购承载商品交易，花粉承载活动与论坛，知识查询归入服务。保留已有双角色维修链与 AI 成果，后续主要投入页面还原、功能闭环和交互打磨，暂停无关 Web 功能的全面迁移及 AI/Agent 扩展。

这属于功能范围收敛和校园场景适配，不能仅靠改导航名称宣称还原完成。与参考 App 的差异应记录到页面对照表，说明用户需求、具体改法和未实现范围。

## 已确认的功能边界

### 选购：二手商品与维修耗材

- 线下付款取货，App 负责真实商品、下单、库存、取消、交付完成与订单查询；不接线上支付、配送、退款资金流。界面明确交易方式，不伪造支付成功。
- 登录用户可发布二手商品，编辑/下架本人商品并处理本人卖家订单；游客可浏览，发布/下单/查看本人订单需登录，登录后续接原操作。管理员可以下架违规商品。
- 商品详情包含真实图片、描述、价格、成色/类别、库存或售卖状态、卖家和取货说明；缺失内容如实呈现。
- 购物订单、报修单 `RepairOrder`、维修备案 `RepairRecord` 是不同对象；不得借用维修进度/审核状态表达购物交易。

**本轮任务规划采用的最小执行口径（可在开工 Issue 中调整并记录）：**

1. 耗材由授权工作人员发布及处理其商品订单；复用交易底座，二手单件库存为 1，耗材支持数量。管理商品权限不扩大为修改所有用户订单。
2. 首版单商品直接下单（耗材可选数量），不同时引入购物车、多卖家合单、议价和私信。
3. 下单成功即“待取货”，线下交付后卖家确认完成；完成前买家可取消，卖家不能交付时填写原因取消。双方只能操作本人相关订单，管理员下架不抹去历史订单。
4. 服务端保存下单时价格/商品快照；重复点击不生成重复单，库存竞争不超卖，取消仅恢复一次库存，下架商品取消后不能意外重新上架。

这些是为了让组员能按小平台范围交付的规划默认值，不是现有接口事实；开工前在交易 Issue 首条进度中确认状态表和角色表即可，不额外加审批流程。

### 活动＋论坛

- 社团发布活动，继续复用已交付的活动浏览、详情、登录报名、本人报名、成员现场处理和管理规则，不重建一套报名模型。
- 登录用户可以发帖、评论；作者可删除自己的帖子/评论，管理员可管理内容。游客可浏览公开帖子，写操作按需登录。
- 第一版提供图文帖子列表、基本分类/关键词搜索、发布、详情、评论、我的帖子；图片为真实上传资源，发布状态来自接口。删除/管理后列表与详情一致不可继续访问已移除内容。
- 不做私信、关注、积分和推荐算法；首版普通评论即可，不扩展复杂楼中楼。帖子评论独立于工作人员内部维修备案评论，不能向论坛公开原备案内容/照片。

1. 先打开参考图，列页面/功能对照；对缺失图片、合理差异及未接入功能如实记录。最终截图与参考图并列，检查层级、间距、字体、图标、卡片、弹层和导航。

3. 每个受影响页面检查加载、真实空态、失败重试、重复点击、返回与登录续接；涉及上传时检查上传/预览。
4. 只做相关必要检查：ArkTS 改动构建 HAP 并做实际模拟器操作；新增写接口验证真实返回、本人/卖家/管理员边界；库存与取消补最小 DB 回归。不为纯文档/样式重跑全库，不做全仓审计，不调用收费模型充当 UI 验收。
5. 保留已有 CI、普通 Merge 和分支规则；源码合入、共享部署、模拟器和真机验证分开陈述。服务器构建仍在本机 WSL/Linux 完成，不在共享服务器安装依赖/构建或清库测试。
