## 3. 已确认业务规则

### 3.1 报修受理、处理与权限

- 所有具备工作人员权限的用户可查看公共待受理队列。先受理成功的人负责后续处理；其他普通工作人员可查看业务授权范围内的报修信息，但不能替其更新。
- 管理员可管理报修单、在合法状态间推进或取消。权限来自服务端现有权限体系；`MEMBER` 不等于管理员，前端传入角色或隐藏按钮都不能代替授权。
- 受理人由服务端通过当前用户的有效 `MemberProfile` 确定，不接收客户端自报受理人。管理员只有 ADMIN 角色、没有有效成员档案时，不能凭空成为受理人或备案作者；其管理已有单据的权限仍保留。
- 本轮不增加转派、多级审批或复杂排班。保持既有转换：

| 当前状态 | 允许进入 |
| --- | --- |
| `SUBMITTED` | `ACCEPTED`、`CANCELLED` |
| `ACCEPTED` | `REPAIRING`、`CANCELLED` |
| `REPAIRING` | `COMPLETED` |

- `COMPLETED` / `CANCELLED` 为终态；不能跳过受理直接完成，不新增维修中取消或重开能力。
- 取消必须填说明；其他推进可填说明。限制长度并保存操作者、变更前后状态、时间及说明，更新 `lastProgressAt`。客户时间线能通过原接口看到变化。
- 报修状态写入与事件写入在同一事务；并发受理只有一人成功，失败者刷新当前状态。重复请求不能重复生成受理或进度事件；用条件更新和必要幂等处理即可。

### 3.2 处理状态与备案状态独立

- 允许报修先标记 `COMPLETED`，随后再补备案；完成不要求备案已提交或审核通过。
- 已受理单可以准备备案草稿，不必等完成才开始记录。未受理和已取消单不新建备案；已关联记录仍按原权限只读查看。
- 页面分别显示“处理状态”和“备案状态：未建档 / 草稿 / 待审核 / 已通过 / 已退回”。不得用备案审核状态冒充客户维修进度。
- 报修处理完成不保证机器已修好。备案结果保留原有 `COMPLETED` / `NOT_COMPLETED`，由工作人员如实填写；不预置成功结果。
- 审核通过或退回不自动改变报修处理状态，也不直接发布到知识库。

### 3.3 备案归属、编辑与关联

- 一个报修单最多关联一个备案，一个备案最多关联一个报修单；重复点击、重试和并发创建不会产生多份或孤立记录。
- 从报修详情创建关联备案时，作者为当前受理人；只允许该受理人创建。管理员若不是受理人，只管理报修和审核，不代其创建或编辑备案。
- 创建备案与建立关联原子完成。客户端不能任意指定其他人的备案 ID 关联。最小化复用现有草稿服务或事务内公共逻辑，不另写一套不同规则。
- 保持原 Web：仅备案本人可编辑 `DRAFT` / `REJECTED`；`PENDING` / `APPROVED` 不可编辑。管理员审核权限不豁免本人编辑限制。
- 保留 `version` 冲突检查、提交与审核的幂等语义。冲突时提示重新加载，不悄悄覆盖他人的结果。
- 设备机型可从报修单预填到已有 `RepairRecord.deviceModel`；维修经过、结果和日期须人工填写或确认。原故障描述只作为参考，不自动当成已完成的维修经过。

### 3.4 字段、照片与审核

- 表单使用已有字段：维修日期、分类、机型、维修内容、结果、耗时、备注；必填和长度限制以实际校验器为准，不自行加收费、根因等新字段。
- 提交审核至少需要有效维修日期、有效分类、非空维修内容、维修结果和一张已上传照片；日期沿用上海日历日语义。草稿允许未填完整。
- 真正选择本机图片、上传并展示持久化结果；编辑状态下可删除误传照片。沿用后端 MIME、实际文件内容、体积和数量限制，不用假 URL、占位图或只保存在页面内的图片充数。无需新增拍照或图片排序能力。
- 受保护照片读取需要会话鉴权；使用现有网络层按平台能力携带 Authorization 或获取图片内容后展示，不把令牌放进 URL，不开放整目录绕过鉴权。
- App 的管理员审核范围：待审核分页列表、备案详情和照片、通过、填写原因后退回、提交中状态与失败重试。退回原因必填。普通工作人员不能调用审核接口。
- 沿用 `DRAFT → PENDING → APPROVED / REJECTED`、`REJECTED → PENDING`；不要求第二个人批准、不增加自审限制、批量审核、导出或审核配置中心。
- 业务备案审核属于 #38；故障卡提取、案例可见范围和发布入索引属于 #40，本轮不实现。

## 4. 开发内容与建议顺序

### A. 后端处理链路

1. 在 `backend/src/features/repair-orders/` 补工作人员队列、我的受理、详情、受理、推进和取消。沿用现有 repository/service/policy/view 分工。
2. 队列支持分页和按处理状态筛选；最低提供“待受理 / 我负责 / 全部”，管理员也能找到需管理的单据。统计若无法真实取得就不展示数字。
3. 新增工作人员路由，例如 `/api/v1/staff/repair-orders`、`/[id]`、`/[id]/accept`、`/[id]/progress`、`/[id]/record`。具体方法和路径可按现有规范决定，先固定契约并同步文档与 App；不要复用客户列表接口返回全部单据。
4. 工作人员详情返回受理信息、时间线、关联备案摘要和允许动作；客户 DTO 维持本人单据的必要信息，不因关联顺便返回内部备案、照片和其他用户资料。
5. 服务端检查身份、受理归属、有效状态与并发条件；现有 `RepairOrder` 没有 version，优先条件更新，不为形式统一额外加字段或迁移。

### B. 复用备案并适配原生通道

1. 复用 `repair-service.ts`、`repair-query-service.ts`、`repair-review-service.ts`、`repair-photo-service.ts` 及实际路由；补关联草稿能力。
2. 只适配 App 实际使用的备案创建、编辑、提交、照片上传/删除、审核等写接口。参照现有 `repair-orders/route.ts`，根据 `readPresentedToken` 的真实 token source 分流：Cookie 保留 `assertSameOrigin`，Bearer 要求 `assertNativeClient`，两者都走真实会话验证。
3. Cookie 与 Bearer 同时存在时保持现有 Cookie 优先规则；不能因为带 native 头就跳过 Cookie 请求的 Origin 校验。不能全局删除 Origin 检查，不能要求 App 伪造 Origin。
4. 读取接口复用现有服务端可见性检查；管理员列表继续要求 `repair:review`。JSON 与 multipart 上传保持原生鉴权一致。
5. 保留现有幂等键位置：成员草稿/提交用 `Idempotency-Key` 头，单条审核用请求体 `idempotencyKey`。不要擅自统一而破坏 Web 调用。

### C. ArkUI 原生页面

1. 工作台接通报修队列和本人处理入口；有审核权限再显示审核入口，角色与允许动作使用会话/服务端数据。
2. 报修详情展示设备、故障、联系方式、受理人、双状态和时间线；按权限展示受理、开始处理、完成、取消、建档/继续备案入口。
3. 备案编辑页支持草稿保存、字段错误、图片选择/上传/删除和提交；已提交或通过后显示只读详情，退回显示原因并可再次编辑。
4. 管理员审核列表和详情支持照片查看、通过及退回，审核后刷新列表与详情；重复审核或别人先处理时给出真实冲突信息。
5. 页面较长时可滚动，键盘不遮挡关键表单和提交；列表能加载下一页、刷新并正确显示空态、初次失败和分页失败。写入期间禁重复提交，失败保留可恢复输入。
6. 打开 A 的详情后关闭并打开 B，A 的迟到响应不能覆盖 B；关闭/退出、筛选变化或重试同样校验请求上下文。避免旧成功、旧失败或旧 finally 改写当前页面。
7. 沿用 `core/auth`、`core/network`、导航、主题；业务放现有 `features/workbench` 或相邻一致目录。共享 ApiClient 按需增加 multipart/图片能力，不另建第二套会话和错误处理。
8. 参考 `docs/reference/my-huawei/` 的服务记录与进度样式，做清楚可操作的原生界面；不要求本轮重画首页或重做 #39 知识问答。共享首页、网络、路由改动尽量小，保留其他模块入口。
