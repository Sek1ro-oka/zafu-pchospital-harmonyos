## 已确认与执行口径

- 线下付款取货，App 内真实下单和订单管理；不接线上支付/配送，不显示假支付成功。
- 登录用户可发布二手、卖家处理本人订单、管理员可下架。游客浏览，写操作/本人订单按需登录。
- 开工先在本 Issue 写简短字段/状态/权限表，采用当前目标文档的规划默认值：二手库存1，耗材支持数量且由授权工作人员发布；首版单商品直接下单、不做购物车/多卖家合单；待取货→完成或取消，卖家确认交付，完成前买家可取消、卖家可附原因取消。
- 若调整这些规划默认值，在 Issue 记录差异；不扩大为支付、物流、私信或议价系统。购物订单独立于 RepairOrder/RepairRecord。

## 交付

- [ ] 原生选购首页：搜索、二手/耗材分类、参考图比例的横幅与真实商品卡、分页/空态/重试；详情展示图片、描述、价格、卖家、库存/成色及取货说明。
- [ ] 二手发布：真实图片上传、标题/说明/价格、本人商品列表、编辑/下架；越权写入由服务端拒绝。耗材维护遵循服务端授权，不能由前端传任意卖家。
- [ ] 商品下单与确认页、我的购物订单列表/详情、卖家订单列表/详情、取消与交付完成；历史商品/价格快照清晰，线下交易方式和允许动作明确。
- [ ] 库存和状态在服务端事务内校验；不超卖、不重复扣减、不重复释放。下单幂等，不能购买本人商品；下架后拒绝新下单，既有订单仍可按规则处理。
- [ ] 管理员真实下架入口及必要原因/反馈；下架/编辑不改写已成立订单的价格快照。取消后只恢复库存，不把已下架商品重新上架。
- [ ] 在自己的模块同时完成列表、详情、表单、图片、状态按钮的参考图样式；接入首页/选购/我的，提供对应 API 契约、非破坏性迁移和课设样本准备方法。

## 必要验收

1. 用户A发布二手→用户B浏览并下单→A看到卖家订单→线下交付确认→B看到完成；切换真实账号，不硬编码身份或订单。
2. 耗材选择数量下单；库存不足/下架不能买。最小 DB 回归覆盖最后一件并发下单、重复提交、取消只释放一次和取消/完成竞争。
3. A/B只能查看/操作相关订单和本人商品；第三人写入被拒绝，普通成员不能使用管理员下架；管理员下架后历史订单仍可查。
4. 页面实际检查真实空态、加载、失败重试、返回/登录续接、图片上传/预览和长标题，不将占位页视为完成。
5. 运行本模块必要 API/DB 检查，构建 HAP并提交买卖双方实际模拟器截图。没有改到的维修、AI和全库无需重测；共享部署单独记录，不在服务器构建。
