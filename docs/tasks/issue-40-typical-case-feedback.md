# Issue #40：典型案例自动整理与知识回流任务书

日期：2026-10-11。对应 [Issue #40](https://github.com/Xiaoyuan-114/zafu-pchospital-harmonyos/issues/40)。本轮由写手实现，技术主线随后审查。

## 1. 目标与本轮决定

实现真实闭环：**维修备案审核通过 → 作者或审核人员标记典型 → AI 整理 → 自动去重或相似合并 → 自动发布 → 换问法检索 → 打开案例与来源依据。**

维护者已确认以下范围，执行时以本轮决定为准：

- 案例来源限已通过审核的维修备案；作者可标记本人备案，具备审核权限的人员可标记业务授权范围内的备案。
- AI 整理去重后直接发布，不增加案例人工编辑、提交审核、退回或二次发布确认。
- 相似案例也自动合并，并保留全部有效来源及各自证据；具体技术判断与必要异常处理见后文。
- 新案例默认内部可见，管理员可以改为客户可见；保留撤回能力。
- 使用现有 DeepSeek、Embedding、关键词与向量检索、本地 MySQL；不新增搜索引擎、独立向量库、任务队列或历史批量导入。

旧基线和历史任务书中的“案例审核/退回”描述是此前方案，不作为本轮新增流程。维修备案自身的审核保持 #38 现有规则。

## 3. 典型标记、归属与可见性

### 3.1 标记权限与入口

- 客户不能标记、处理、重试或管理案例。工作人员仅能标记/取消本人 APPROVED 备案；审核人员可操作其他 APPROVED 备案。
- 使用服务端用户身份、备案归属、状态和实际权限判定；不接受客户端传入作者或角色作为授权依据。
- 给 App 提供独立的典型标记动作或细粒度服务，作者只改变 isTypical，不能借此改变 isDifficult、备案正文、审核状态或他人备案。不要把 `repair:flag` / `repair:review` 整体授予 MEMBER。
- 原 Web 管理员标记接口仍按原契约使用；课设后端各处 isTypical 写入要共同驱动处理/失效逻辑。保留原 Web Cookie + Origin 和原生 Bearer + native 头的来源规则，复用 `assertWriteAccess`。
- 已标记且内容未变时再次点击，取回当前处理状态或结果，不重复调用模型和创建案例。历史已经标记的记录可通过本轮单条处理入口触发，不强制全库回填。

### 3.2 默认范围与管理

- 新案例为 `STAFF`；工作人员/管理员可读，客户不可读。管理员可将有效案例设为 `PUBLIC`，也可改回内部。
- 自动寻找重复和相似案例时限定相同可见范围，内部贡献不会自动混入公开案例。管理员显式调整一个案例的范围时，该决定适用于其当前完整内容和来源证据。
- 客户来源详情只展示已公开案例及可公开证据，不因此获得原备案、人员联系方式、照片的读取权限；工作人员查看原备案继续走原有接口授权。
- 管理员可撤回案例。撤回立即阻止新的检索命中和来源读取；普通重试、程序重启、索引重建不能自动恢复管理员撤回的案例。恢复由管理员明确触发重新整理发布，可复用管理动作，不新增审批。
- 本轮不提供自由编辑案例正文的页面。修改事实通过原备案既有规则完成，再触发重新整理。

## 4. AI 整理与多来源证据

### 4.1 输入及输出

以实际备案字段为基础，整理：标题、机型/适用设备、故障现象、排查过程、原因、处置、维修结果、分类和证据。不能把客户原故障描述自动当成已完成的维修经过。

- 只输入完成该任务需要的备案文字字段和受控来源 ID；照片第一版不参与视觉分析，原照片继续由原接口提供。
- 原记录没有明确给出的原因、排除项、机型等保持未知；`NOT_COMPLETED` 原样保留，不从“报修已完成”推断已经修好。
- 模型输出必须解析和校验类型、长度、来源 ID 与证据片段。引文应可定位到输入字段/原文片段；禁止模型生成不存在的来源或凭空补维修事实。
- 保留来源内容快照/内容哈希、提取或合并使用的模型和提示词版本。用来源内容哈希判断实质变化，不能把一次标记引起的 version 自增误判成正文变化而无限重整。
- 原文与已有案例正文作为资料输入，不能覆盖系统任务指令；模型不直接写数据库、不决定权限和可见范围。
- 模型不可用、超时或结构化输出不合格时记录失败并提供重试；不得用硬编码案例、空内容或假成功替代。

### 4.2 去重与自动合并

1. **来源去重**：同一备案、同一实质内容只处理一次；重试复用已有结果。
2. **完全重复**：使用可复现的内容归一化/哈希判定，复用已有案例并增加来源关联，不重复生成独立案例。
3. **相似候选**：复用已有向量检索能力，结合机型/分类/故障文字筛选少量候选，建议最多 3 个。记录阈值与小样本结果；#39 的向量相关性阈值 0.6 不是自动合并阈值，不能直接等同。
4. **合并判断**：把新来源及候选案例的有效来源证据交给模型，结构化返回“合并到某一候选/新建”及依据。服务端校验目标在候选白名单、状态和范围有效，再执行结果。
5. **正文更新**：基于合并后全部有效来源生成案例，而非只拼接旧摘要。保留每个来源的 ID 和证据对应关系；不同结果或条件按来源分别说明，不能将不同记录的检查步骤串成一次维修经历。

相似度高不等于同一个故障；机型近似但处置不同、原因未知或结果相反时，允许保留差异说明或新建案例。判断由自动流程完成，不加人工合并队列。

已有多来源案例新增贡献时复用其案例身份并更新内容版本。第一版每次处理至多合入一个目标案例，不必做全库聚类或跨多个已有案例的大规模重组；最终所属案例仍需包含全部实际合入的来源。

## 5. 数据、一致性与失败重试

建议新增案例表和来源关联表，命名可按项目规范决定。至少保存：

| 对象 | 必要内容 |
| --- | --- |
| 案例 | 稳定 ID、结构化正文/展示正文、STAFF/PUBLIC、可检索/撤回/需重整状态、内容版本、模型/提示词信息、时间 |
| 来源贡献 | 原 RepairRecord ID、对应案例 ID、实质内容哈希/证据快照、处理状态、失败原因、处理代次/锁或等效并发控制 |

- 一个来源当前至多归属一个有效案例；多个来源可归属同一案例。用数据库约束保护，不仅靠前端禁按钮。
- 标记后自动调用处理流程；页面显示整理中、已入库、失败/重试等真实状态。采用单条处理 API 和持久化状态即可，不引入 Redis、后台队列、定时批处理或新部署服务。
- 使用明确的单次处理总预算和客户端超时；模型调用放在数据库长事务之外。服务重启、请求断开、超时或长期处理中后，状态可识别并安全重试，不能永久锁死。
- 来源标记与处理状态可靠持久化；发布正文、来源关联和案例版本原子提交。并发处理同一来源不生成重复案例；两条相似来源同时合并时不覆盖或漏掉其中一条贡献。
- 写入前在事务内复核来源仍 APPROVED、仍典型、内容哈希未变，目标案例仍有效、范围未变、版本未变。模型生成期间管理员撤回、来源取消典型或内容修改后，旧结果不能继续发布。
- 冲突时有界重读/重试，超预算返回可恢复状态；不盲目重复付费模型请求、不在没有版本校验时覆盖最新案例。
- 原备案改动/软删/取消典型后，受影响的旧案例立即停止新的检索及来源读取，移除该贡献并自动基于剩余有效来源重新整理；无有效来源则撤下。有剩余来源但重整失败时显示失败并允许重试，不能继续提供已失效证据。
- 原 Web 管理修改和软删路径也要生效；只改 App 标记入口不足以保证回流一致性。

## 6. 接入现有检索与引用

- 案例数据以 MySQL 为权威。可以在查询时装配案例块或更新现有索引，选择代码量较小且满足一致性的方案，复用 #39 的排序与模型调用。
- 发布后无需人工执行命令才能首次检索到案例；关键词先可用，向量生成成功后加入混合检索。向量失败时准确显示状态并提供单条重试，不能声称向量已生效。
- 案例 embedding 使用既有 provider/model，复用未变内容的缓存；不能用与现有文档不同维度的向量硬混。无 embedding 配置时说明降级范围，正常关键词能力可交付。
- 管理员调整范围、撤回或来源失效时，以当前数据库状态收口检索候选和来源详情；旧 JSON、内存缓存、旧引用 ID 都不能继续提供已撤回/无权资料。必要时在调用模型及返回来源前复核有效性。
- 文档与案例参与同一检索和回答；文档快照及 `knowledge:sync` / `knowledge:index` 保持可用，重建文档索引不应误删案例。
- 引用标注保持 #39 的 S1/S2 编号契约。案例使用明确的来源类型、案例 ID 和内容版本/块 ID，正文变化后旧版本引用按过期处理；提供友好提示，不静默指向新内容。
- 案例引用详情展示本次引用的案例与逐条来源证据；原始备案入口只提供给具有原权限的账号。不生成伪造 GitHub 原文链接。
- 新一轮问答及引用访问必须执行当前范围检查；已显示在本次对话中的历史文字不承诺远程擦除，也不能把历史文字当成仍然有效的检索证据。

## 7. 原生页面与接口交付

### App

1. **备案详情**：按服务端能力展示典型标记/取消、自动处理进度、失败重试及关联案例入口。作者仅本人可操作；审核人员可操作已审核备案，审核页完成通过后可标记。
2. **工作台案例列表**：分页、按实际支持的范围/状态筛选、案例详情、多来源及证据、处理失败的入口。不展示假统计。
3. **管理员管理**：切换内部/公开、撤回及显式恢复处理；执行期间禁重复操作，权限/版本冲突显示真实提示。
4. **知识引用详情**：兼容文档与案例，多来源清晰展示；客户原备案权限边界保持不变。

保留加载、空态、初次失败、分页失败和重试；长内容可滚动。异步响应绑定来源/案例 ID 与页面代次，关闭、切换对象或退出后不回写新页面；刷新时释放旧代分页锁。失败重试保留其原目标和操作模式。沿用现有会话过期处理、主题与网络层。

### API 与组织

- 后端业务建议放 `backend/src/features/knowledge-cases/`，检索适配留 `features/knowledge/`，备案标记及内容失效复用现有 repairs 服务。
- App 建议放 `features/knowledge-cases/` 或相邻一致目录，共享导航/网络最小化修改。
- 提供典型标记、单条处理/重试及状态、案例列表/详情、管理员范围和撤回动作；具体路径/方法自行按项目习惯确定，先落实契约再接页面。
- 新写接口复用 `assertWriteAccess` 和真实会话授权，读取检查范围；原 Web 的 PATCH 可以保留，原生需要时可沿用 POST 别名并共用处理逻辑。

优先复用现有测试框架，只覆盖本次变化及受影响链路。CI 模型调用使用模拟依赖，不调用付费服务；实际模型与真实库另外做小样本验证。

| 检查 | 最低覆盖 |
| --- | --- |
